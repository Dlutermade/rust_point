# 00 — 願景與問題

> 商業視角:這門生意解什麼問題、為誰創造價值。零技術(SSR / SEO 這類非功能需求因涉商業價值會提及,但不談實作)。
> ⚠️ 早期草擬,邊寫邊跟 PO 核對。

## 問題

商家的前台(門面)要能自己客製,但傳統 CMS 多半只能改**內容**(填字、換圖):版型是固定模板、促銷要放哪也綁死。商家其實想要:

- 自由組合頁面**結構**,不只填內容。
- 控制**排版**與**曝光版位**——什麼促銷 / 內容,出現在哪個位置。
- 前台還要**被搜尋引擎找得到(SEO)、載入快**。

## 前台中心是什麼

一個**可客製化的前台頁面系統——像 EDM 編輯器,但做的是網站前台**:

- 商家在後台**拖拉區塊**拼出頁面;頁面 layout 以**樹(Tree)**組成(頁 → 區塊 → …)。
- 客製化 = 商家 **DIY 拼區塊**:一組區塊(Hero、banner、文字清單、最新消息、(未來)商品清單…)**本身就是曝光版位**,商家排哪些、怎麼排,就決定「如何曝光」。比傳統 CMS(只管內容)更進一步——連結構與曝光都自訂。
- **互動由商家指定**:放了按鈕之類的互動元素,商家要能設定「按下去做什麼」(去結帳 / 開新分頁 / 去登入…)——系統無法猜意圖,故提供一組動作讓商家挑。(動作目錄與 routing 實作屬技術。)
- 支援**第三方腳本**的編排。

## 頁面類型與建置順序

先做**共用框架**,再逐一做各種頁:

1. **header / footer**(共用框架,先做)
2. **首頁**
3. **活動頁**
4. **自訂頁**
5. **商品頁**、**商品分類頁**(等商品中心就緒後回來補)
6. …依此類推

## v1 區塊(還沒有商品)

- **banner(含 Hero)**、**文字清單(如最新消息)**、**圖片**、**排版容器**(讓區塊並排 / 巢狀)。
- 商品相關區塊(如商品清單)等商品中心接上前台時才補。

## 產品級非功能需求(NFR)

- **SEO**:前台頁面要被搜尋引擎找到 → 內容要能在伺服器端就出得來(SSR)。SEO = 流量 = 商業價值。
- **載得快**:只載入頁面**實際用到**的區塊 / 腳本,沒用到的不載。

> 這些「怎麼做」(SSR、lazy load、Rust + React、腳本載入器、event routing)屬**技術視角**,商業層只立需求、不談實作。

## 價值主張

- 商家自助客製門面,不受固定模板限制。
- 內容、排版、曝光版位**一站編排**;區塊可互動。
- 作為**整合底座**:商品、訂單、(未來)點數等中心,都在前台這裡顯化。

## 適用對象

**多租戶**:一套系統服務多個商家,每個商家有**各自的站**(頁面、版位、客製各自獨立)——與 point-center 同。
